# Alceo — Backend

Alceo is a web app that logs workouts and uses AI to generate future ones. It serves both people who train on their own and trainers. This repo is the Python backend: a REST API consumed by the web frontend.

School project, due **October 15, 2026**. Favor working, simple code over abstractions.

## Stack

- Python 3.12, Flask (app factory + blueprints)
- SQLAlchemy 2.0 (typed `Mapped[...]` models) + Alembic for migrations
- Postgres 18 on Neon, project **"Workout Log"**, driver `psycopg` (v3)
- Gemini API for workout generation (`google-genai`), default model `gemini-2.5-flash`
- Passwords hashed with argon2 (`argon2-cffi`); Google sign-in supported
- pytest for tests

## Layout

```
app/
  __init__.py        # create_app()
  config.py
  db.py              # engine, session
  models/            # one file per table
  routes/            # blueprints: auth, users, filters, exercises, workouts, ai
  services/          # business logic (ai.py, workouts.py, auth.py)
  schemas/           # request/response validation
migrations/          # Alembic
tests/
```

Routes stay thin: validate input, call a service, return JSON. Business rules live in `services/`.

## Database

The source of truth for the schema is the Notion page **"Alceo 1.1"** (mirrored in `alceo_1_1_schema.sql`). Models must match it exactly. If they disagree, ask before changing either one.

Tables: `users`, `user_filters`, `exercises`, `ai_queries`, `workouts`, `workout_exercises`, `workout_sets`.

```
users 1─* user_filters
users 1─* ai_queries 1─* workouts 1─* workout_exercises 1─* workout_sets
users 1─* workouts            exercises 1─* workout_exercises
users 1─* exercises (custom, via created_by_user_id)
```

### Rules

- All PKs are `INT GENERATED ALWAYS AS IDENTITY`. Never set `id` on insert.
- CHECK-constraint values live in one place, `app/models/enums.py`, and must match the DB exactly:
  - `users.role`: athlete, trainer (demo is athlete only)
  - `users.sex`: male, female, other
  - `users.status`: onboarding, active, blocked, deleted
  - `user_filters.filter_type`: injury, weight_goal, venue, training_component, schedule, sport, benchmark, equipment
  - `exercises.category`: strength, cardio, mobility
  - `exercises.equipment`: barbell, dumbbell, kettlebell, machine, cable, band, bodyweight, other
  - `workouts.status`: planned, in_progress, completed, abandoned
  - `ai_queries.status`: pending, success, error
- **Equipment vocabulary is shared.** Equipment filters use the same words as `exercises.equipment` so the AI can match them. Never add a free-text equipment word.
- **Units:** store kg, meters and seconds only. Convert to lb/miles in the frontend.
- **Soft delete, not hard delete:** `exercises.is_active`, `user_filters.is_active`, `users.status = 'deleted'`. Logged workouts reference exercises, so exercises are never deleted.
- `workout_exercises.exercise_id` has no cascade on purpose. It protects workout history.
- `workouts.finished_at >= started_at`. `started_at` is NULL while planned, `finished_at` is NULL while in progress.
- `sort_order` is unique per workout, and `set_number` is unique per workout exercise. When reordering, renumber inside one transaction.
- **Warm-ups are not a separate screen or table.** They are `workout_sets` rows with `is_warmup = true` inside the same workout.
- `rpe` is between 1 and 10 (one decimal).
- **Age gate:** age is derived from `date_of_birth`. Failing the gate sets `status = 'blocked'`.
- New users start in `status = 'onboarding'`. Profile fields (sex, DOB, height, weight) are filled during onboarding, then status becomes `active`.

### Migrations

- Every schema change goes through Alembic. No hand edits on the live database.
- Review autogenerated migrations before running them, because autogenerate misses CHECK constraints.
- **Never run destructive SQL (DROP, TRUNCATE, DELETE without WHERE) against the main Neon branch.** Test on a Neon branch first, and ask before touching main.

## AI workout generation

Flow for every AI call (`services/ai.py`):

1. Insert an `ai_queries` row with `status='pending'`, `system_prompt`, `user_prompt` and `model`.
2. `system_prompt` holds the fixed coach instructions: respect injuries, only use the user's listed equipment, warm-up first, reply in the JSON format.
3. `user_prompt` holds this user's data at that moment: profile, **active** filters only, recent workouts, and the request.
4. Call Gemini with two messages (role system, role user) and request JSON output.
5. On success: store the raw reply in `response` (JSONB), set `status='success'`, then create a `workouts` row with `status='planned'` and `ai_query_id` set, plus its exercises and sets.
6. On failure: `status='error'`, `error_message` (max 500 chars), `response` stays NULL. Never create a workout.

Validate the AI's JSON before inserting anything. Unknown exercise names or equipment outside the allowed list get rejected or mapped, never inserted blindly. Keep the prompt-building code pure and unit-tested.

A workout with `ai_query_id IS NULL` was built by the user.

## Security

- Never store, log or return a plain password, and never return `password_hash` in any response.
- `password_hash` is NULL for Google-only accounts. Password login must reject those users cleanly.
- Every query on user data filters by the authenticated `user_id`. A user can never read or edit another user's filters, workouts or AI queries.
- Use parameterized queries (SQLAlchemy) only, with no string-built SQL.
- Secrets come from env vars only.

## Conventions

- JSON in snake_case, matching column names.
- Timestamps are `TIMESTAMPTZ` and returned as ISO 8601 UTC.
- Errors use the shape `{"error": {"code": "...", "message": "..."}}` with a correct HTTP status.
- Type hints everywhere. Small functions.
- Tests cover services and constraint edge cases (RPE out of range, `finished_at` before `started_at`, duplicate `sort_order`, cross-user access).
